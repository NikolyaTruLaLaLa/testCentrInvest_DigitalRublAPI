# README — Микросервис учёта кошельков цифрового рубля

## Описание

Микросервис предназначен для учёта цифровых кошельков клиентов банка. Он предоставляет HTTP API для оператора банка и для обмена данными с платформой цифрового рубля (ЦР). Реализован на **.NET 10** с использованием **чистой архитектуры** (Clean Architecture) и элементов **DDD**.

Основные возможности:
- Просмотр списка клиентов с пагинацией и поиском.
- Просмотр кошельков конкретного клиента.
- Приём данных от платформы ЦР (создание/обновление кошельков).
- Обновление статуса и/или номера счёта кошелька.
- Простой веб-интерфейс на **vanilla JS** для демонстрации работы API.
- Широкие автотесты для всех слоёв.

## Как запустить API и UI (Windows)

### 1. Клонирование репозитория

```bash
git clone <url-репозитория>
cd testCentrInvest_DigitalRublAPI
```

### 2. Поднятие PostgreSQL

Убедитесь, что PostgreSQL установлен и запущен. Можно использовать локальную установку или Docker:

```bash
docker run --name postgres-db -e POSTGRES_PASSWORD=ваш_пароль -p 5432:5432 -d postgres
```

Создайте базу данных (или дайте приложению создать её автоматически при первом запуске).

### 3. Настройка строки подключения

Приложение использует **User Secrets** для разработки и **переменные окружения** для запуска вне Visual Studio.

#### 3.1. Для WebAPI (User Secrets)

В папке `WebAPI` выполните:

```bash
cd WebAPI
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Host=localhost;Port=5432;Database=DigitalRubleDb;Username=postgres;Password=ваш_пароль"
```

#### 3.2. Для Infrastructure (системная переменная)

Так как Infrastructure не имеет своего `appsettings.json`, необходимо задать системную переменную окружения:

```cmd
setx ConnectionStrings__DefaultConnection "Host=localhost;Port=5432;Database=DigitalRubleDb;Username=postgres;Password=ваш_пароль"
```

> **P.S.** Это временное решение (костыль), на которое я пошёл из-за особенностей загрузки конфигурации в слое Infrastructure. При наличии большего времени я бы устранил эту необходимость, передавая конфигурацию через DI более элегантно.

### 4. Запустите приложение

В корневой папке решения выполните:

```bash
dotnet run --project WebAPI
```

При первом запуске автоматически:
- Создаст базу данных (если её нет).
- Применит миграции.
- Добавит начальные данные (3 клиента с кошельками) через `DbInitializer`.

### 5. Откройте UI

В браузере перейдите по адресу:  
[http://localhost:5261](http://localhost:5261)  
(порт может отличаться, проверьте вывод в консоли).

### 6. Документация API (Swagger)

Swagger доступен только в режиме **Development** по адресу:  
[http://localhost:5261/swagger](http://localhost:5261/swagger)

### HTTP API

Все эндпоинты имеют префикс `/api`.

| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/Clients` | Получить список клиентов с пагинацией и поиском. Параметры: `pageNumber` (по умолчанию 1), `pageSize` (по умолчанию 10), `searchTerm` (опционально, поиск по mid и ФИО). |
| `GET` | `/Clients/{mid}/wallets` | Получить все кошельки клиента по его `mid`. |
| `POST` | `/platform/wallet` | Отправить данные от платформы ЦР. Тело: `{ mid, participantDRId, walletCode, status, accountNumber? }`. Если у клиента нет активного кошелька — создаётся новый. Если есть — обновляется существующий. |
| `PUT` | `/platform/wallet/{code}` | Обновить статус и/или номер счёта кошелька. Тело: `{ mid, newStatus?, accountNumber? }`. `newStatus` опционален — можно обновить только номер счёта. |

Все ответы возвращаются в формате JSON. Ошибки предметной области (например, дубликат кошелька, недопустимый переход статуса, повторная установка номера счёта) возвращаются с HTTP-статусом 400 и понятным сообщением.

### Модель данных

База данных состоит из двух основных таблиц:

#### `Clients`

| Поле | Тип | Ограничения | Описание |
|------|-----|-------------|----------|
| `Id` | UUID | PK | Идентификатор клиента |
| `Mid` | VARCHAR(255) | UNIQUE, NOT NULL | Межсистемный идентификатор клиента |
| `LastName` | VARCHAR(200) | NOT NULL | Фамилия |
| `FirstName` | VARCHAR(200) | NOT NULL | Имя |
| `Patronymic` | VARCHAR(200) | | Отчество (может быть пустым) |
| `ParticipantDRId` | VARCHAR(255) | UNIQUE, NULLABLE | Идентификатор участника на платформе ЦР (задаётся один раз) |

#### `Wallets`

| Поле | Тип | Ограничения | Описание |
|------|-----|-------------|----------|
| `Id` | UUID | PK | Идентификатор кошелька |
| `ClientId` | UUID | FK → Clients.Id, NOT NULL | Владелец кошелька |
| `Code` | VARCHAR(255) | UNIQUE, NOT NULL | Код кошелька на платформе ЦР |
| `Status` | VARCHAR(4) | NOT NULL | Статус: `Prcs`, `Actv`, `Blck`, `Clsd` |
| `AccountNumber` | VARCHAR(50) | UNIQUE, NULLABLE | Номер счёта (задаётся один раз) |

**Связи:** один клиент может иметь много кошельков. Каскадное удаление включено (при удалении клиента удаляются все его кошельки).

### Допущения и принятые решения

1. **Активность кошелька:** активными считаются статусы `Prcs` (ожидает открытия), `Actv` (активен) и `Blck` (заблокирован). Статус `Clsd` (закрыт) является финальным и неактивным.

2. **Один активный кошелёк:** у клиента не может быть одновременно двух активных кошельков. При попытке создать новый активный кошелёк, если уже есть активный, выбрасывается исключение. Это правило реализовано на уровне домена в методе `Client.AddWallet()`.

3. **Уникальность:** код кошелька (`Code`) и идентификатор участника (`ParticipantDRId`) должны быть уникальными в пределах всей системы. Номер счёта (`AccountNumber`) тоже уникален, если задан. Все уникальные ограничения настроены на уровне БД через индексы.

4. **Номер счёта:** может быть задан только один раз для каждого кошелька. Повторная попытка установить номер счёта приводит к ошибке `DomainException`. Реализовано в методе `Wallet.SetAccountNumber()`.

5. **Переходы статусов:** строго регламентированы таблицей переходов:
   - `Prcs → Actv`
   - `Actv → Blck`
   - `Blck → Actv`
   - `Blck → Clsd`
   - Из `Clsd` переходы невозможны.
   Реализовано через статусную машину в доменном слое (словарь допустимых переходов).

6. **Архитектура:** использована чистая архитектура с разделением на слои:
   - **Domain** — сущности, репозитории (интерфейсы), доменные исключения, бизнес-правила.
   - **Application** — сценарии использования (CQRS через MediatR), DTO, маппинг (AutoMapper), валидация (FluentValidation).
   - **Infrastructure** — реализация репозиториев (EF Core), конфигурация БД, миграции, инициализация данных.
   - **WebAPI** — контроллеры, middleware, Swagger, статические файлы (frontend).

7. **Инициализация БД:** начальные данные (3 клиента с кошельками) добавляются через `DbInitializer` при первом запуске, если таблица `Clients` пуста. Миграции применяются автоматически через `dbContext.Database.Migrate()`.

8. **Строка подключения:** для WebAPI используется User Secrets (в разработке), для Infrastructure — системная переменная окружения. Это временное решение, требующее доработки в будущем.

9. **Тестирование:** покрыты модульными тестами доменная логика (`Domain.Tests`) и все сценарии Application (`Application.Tests`). Тесты используют моки репозиториев и не требуют реальной БД.

### Как это работает: сценарии

1. **Список клиентов:** оператор открывает страницу → автоматически загружается список клиентов. Можно искать по ФИО или mid, переключать страницы.

2. **Кошельки клиента:** оператор кликает по строке клиента → загружаются его кошельки с кодами, статусами и номерами счетов.

3. **Приём данных от платформы ЦР:** заполняется форма → отправляется POST-запрос. Если у клиента нет активного кошелька — он создаётся. Если есть — обновляется. Устанавливается идентификатор участника (если ещё не задан).

4. **Обновление статуса/номера счёта:** заполняется форма → отправляется PUT-запрос. Можно изменить только статус, только номер счёта или оба поля одновременно. Номер счёта устанавливается только если ещё не задан.

Все операции проверяют бизнес-правила и возвращают понятные ошибки при нарушениях.

## Что бы улучшили при большем времени

- **Устранение костыля с переменной окружения:** передавать конфигурацию в Infrastructure через DI более элегантно.
- **Более широкое покрытие тестами:** покрытая большая часть TestCases, но не вся.
- **Логирование и мониторинг:** внедрение Serilog с записью в файл и, возможно, в ELK-стек.
- **Обработка ошибок и валидация:** улучшить централизованную обработку ошибок, добавить более детальные кастомные исключения.
- **CD:** настроить пайплайн GitHub Actions для автоматического деплоя.
- **Rate Limiting:** добавить ограничение частоты запросов, чтобы защитить API от перегрузок.
- **Фронтенд:** улучшить UI, добавить уведомления (toast), адаптивную вёрстку и более удобные формы.
